# Optional project document catalog

Read this catalog before recommending or creating a shared project reference and during completion to identify affected documentation. This is the shared index for project-level documentation. Paths in code spans are relative to the repository root. The [workflow Phase 3 table](../WORKFLOW.md#phase-3-specify-after-accepted-scope) covers feature-level optional files (`DESIGN.md`, `RESEARCH.md`, and `HANDOFF.md`). Templates are installed for reuse; initialization does not create the completed project documents below.

Before creating a shared reference, check whether an existing README, contributing guide, design system, publishing guide, runbook, or other maintained source already serves the purpose. Use that source even if its filename differs. When a catalog trigger fits the current work and a shared reference would help future work, create a concise document as part of the authorized specification or implementation. Routine supporting documentation needs no separate approval. Ask when creating it would require unresolved product decisions or materially expand the scope. Start with what is known and useful; a document does not need to be comprehensive to earn its place. Updating an existing affected reference is part of completing the change. ADRs follow their adoption rule below, not a separate optional-document approval gate.

| Document                         | When it adds value                                                                                                                     | Ownership and use                                                                                                                                                                                                                                                                            |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docs/ARCHITECTURE.md`           | The implemented system needs an overview of components, boundaries, and data flows.                                                    | Read for cross-cutting implementation work; update when the system changes. Describe current architecture and link to ADRs for rationale.                                                                                                                                                    |
| `docs/GLOSSARY.md`               | Domain terms recur across features or are easily confused.                                                                             | Own precise shared meanings; consult during specification and update when domain language changes.                                                                                                                                                                                           |
| `docs/VISUAL_DESIGN.md`          | Shared visual conventions are being defined or changed and no existing design-system reference suffices.                               | Read before UI work; maintain shared conventions when they change. Ground them in the interface and agreed direction, distinguish proposals from adopted rules, and leave feature-specific interactions in `DESIGN.md`.                                                                      |
| `docs/TESTING.md`                | Verification setup, check selection, or integration boundaries need explanation beyond scripts and CI.                                 | Read before planning/running verification; maintain reusable procedures and limitations. Scripts/CI own executable commands; feature acceptance criteria documents own results.                                                                                                              |
| `docs/PRODUCT.md`                | Users, purpose, core journeys, principles, or deliberate non-goals are unclear from existing documentation.                            | Read before scope decisions; update for agreed direction or implemented journey changes. Distinguish current capabilities from future direction and proposals. This is not a roadmap or feature approval mechanism.                                                                          |
| `docs/DEPLOYMENT.md`             | Recurring release, deployment, or recovery procedures need explanation beyond existing automation or publishing/runbook documentation. | Read for release-impacting changes; maintain rollout order, compatibility, migrations, post-release checks, and recovery limits. Feature plans own deviations; acceptance criteria documents or linked release records own execution evidence. Procedures do not grant execution permission. |
| `docs/conventions/<topic>.md`    | A stable, non-obvious rule applies across features and is not adequately enforced or documented elsewhere.                             | Read for relevant changes; maintain reusable rules. Tooling owns mechanically enforced rules; feature plans or ADRs own feature-specific decisions.                                                                                                                                          |
| `docs/adr/adr-NNN-kebab-case.md` | A significant architectural decision has actually been adopted.                                                                        | Record rationale at adoption under the agreed workflow; preserve history and link superseding decisions. Keep unimplemented proposals in feature plans.                                                                                                                                      |

Use `.agent-specs/templates/project/` for the six named project references, `templates/conventions/CONVENTION.md` for conventions, and `templates/adr/ADR.md` for decisions (all under `.agent-specs/`). Fill templates from actual project context and remove irrelevant guidance; keep the first version concise and substantive rather than filling every template section.
